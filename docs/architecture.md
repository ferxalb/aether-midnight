# Architecture and data flow

Midnight is one local Rust engine. The CLI, MCP server, and examples call the same core code and use the same SQLite schema.

## Four layers

1. **Sources and scopes.** A repository is identified by its canonical root and Git common directory where available; a worktree gets its own identity. Repository and worktree identifiers are mandatory columns in code index lookups. Agent memories use an explicit caller namespace (for example `user:alice` or `project:payments`) in every query. Raw source rows and derived facts are distinct; derived rows can cite a source row or URI and can supersede an earlier fact while retaining its history.
2. **Deterministic indexes.** SQLite stores file metadata, a contentless FTS5 `unicode61` token index, extracted symbol spans, and a separate FTS5 memory index. The code index retains token postings without storing whole source text; snippets are read from the current file. Exact paths and symbols have dedicated lookups. Tree-sitter extraction runs for Rust, Python, TypeScript, and TSX. Other file types remain searchable lexically and are labelled by extension; they do not receive structural parsing in v1.
3. **Retrieval and context packing.** Candidate scores expose path, symbol, and lexical contributions. Results carry repository/worktree scope, index generation, completeness, freshness, source path, and current-file snippets where the indexed content hash still matches. `open_range` reads current source. Search snippets are packed under a deterministic heuristic token budget; the estimate is not a model tokenizer.
4. **Agent interfaces.** The CLI and stdio MCP adapter expose the same operations. Node.js, Bun, and Go client examples are provided; their runtime verification is pending (not run) in the latest Linux benchmark run.

## Index flow

`index` walks one root with Git ignore/exclude behavior and `.aetherignore`, filters default exclusions, checks file type/size and repository containment, reads at most 1 MiB, hashes and optionally parses it, then writes bounded SQLite batches. On Unix, repository-relative file access opens each directory component from a root handle with `openat(O_NOFOLLOW)`, so a raced symlink cannot redirect a read outside the root. The walker also does not follow symlinks. VCS metadata directories remain excluded even with `--include-generated` because their config can contain credentials.

Indexing uses a bounded parallel preparation pipeline and one SQLite writer. The worker count defaults to available parallelism, capped at 12, and can be set with `MIDNIGHT_INDEX_WORKERS`. Job and result queues are limited to twice the worker count. In-flight jobs reserve up to three times source size against an 8 MiB budget; pending writer batches are capped at 512 changed files or 16 MiB of source text. These are internal admission limits, not a strict RSS ceiling: Tree-sitter working state, allocator overhead, SQLite state, and file cache are not fully represented. The writer prepares its file metadata and symbol statements once per transaction batch.

Each successful full scan advances a generation. Rows not seen in that generation are removed, including files deleted or newly ignored since the prior scan. A canceled scan leaves `catalog_complete=false`; it does not perform generation reconciliation. Progress rows are published while scanning so a separate process can search the same WAL database and see explicitly partial results. MCP calls within one stdio process are handled serially, so use a second process if indexing and search must overlap.

For an empty/incomplete index, search tries scoped indexed candidates first, places eligible paths in a SQLite disk-backed temporary table, then reads them in path order until it finds the first match. It returns that bounded result with `fresh_unindexed`, `index_complete=false`, and a truncated response flag; the temporary candidate list disappears with the connection. Index the repository to retrieve a ranked multi-result set.

## SQLite and format

SQLite is built from the pinned `rusqlite` bundled SQLite dependency, with FTS5. Database schema migrations use one immediate transaction. `PRAGMA user_version`/`metadata.schema_version` identify schema `6`; `metadata.index_format_version` remains `2`, because that version describes the code index. Schema 2→3 transactionally rebuilds active memory postings into a scoped `contentless_delete=1` FTS table, retaining memory rows, provenance, validity, and supersession links. The earlier v1 trigram-to-`unicode61` migration drops unrebuildable code postings, clears the file catalog, and marks repositories incomplete so a full reindex is required. WAL mode provides readers during short indexing commits. `compact` clears forgotten memory content, optimizes both FTS indexes, truncates the WAL, and vacuums the database. Schema 3→4 adds `memory_scope_counts`, trigger-maintained active-memory counts per namespace (an empty-string row holds the total), backfilled in the same migration transaction; it adds one SQLite page and about 0.07 ms to a single `remember`. Schema 5→6 adds the `embeddings` table (persistent vectors with model, revision, dimensions and source hash) and triggers that delete vectors when their memory or code file is deleted or changed; see `docs/embeddings.md`.

The memory FTS table stores a SHA-256-derived namespace token and searchable terms, not a second copy of full memory text. Queries still verify the exact namespace on the memory row. `MemorySession` opens one configured SQLite connection per long-lived MCP process and reuses cached statements for memory calls; it is created lazily and the current MCP request loop remains serial. The path-based CLI calls remain one-shot. `remember_batch` validates a bounded batch (512 records/16 MiB) before one transaction and rolls the whole batch back on an insertion or provenance error.

Memory recall normalizes Unicode and accents, removes common English/Spanish terms for matching, safely quotes up to 64 terms, and returns no candidates when nothing searchable remains. Final ordering is lexicographic: contiguous full-query phrase, then the number of distinct informative terms, then BM25 within that class, then temporal and provenance tie-breaks. Because the class dominates BM25, production recall (v0.4) enumerates classes best-first with FTS5 phrase/AND queries (phrase, all terms, then at-least-m-of-n down to two) and stops once the requested limit is filled; BM25 only orders rows inside a class. Each stage is a top-N over `(rank, rowid DESC)` taken entirely inside the FTS5 columns, then `LEFT JOIN`s only the winners to apply the exact namespace, non-deleted, and validity-time predicates, so rows that lose never touch the `memories` table. Exact BM25 ties therefore resolve to the most recently remembered rows, independent of content and insertion batching. Up to four informative terms use per-class stages (or one read of the whole eligible set when at most 128 rows qualify); longer queries use the uniform any-term expression over one bounded window of five times the limit (at most 500) and are labeled `bm25_top_k`. When the namespace holds at least half of all memories the `scope_token` term is omitted from the FTS expression, because walking a namespace-sized posting list costs more than it prunes; `m.scope = ?` still enforces the boundary. `candidate_coverage` is `complete` only when every stage ran to exhaustion, `exact_top_k` when the returned list is the exact top-k under this ordering but lower classes were not enumerated, `bm25_top_k` for the bounded long-query window, and `recency_window` only for the opt-in `broad_terms: "recent"` shortcut. See `docs/retrieval-v04.md` for guarantees, measurements, and rejected designs.

The reranker prioritizes a contiguous full-query phrase, then the number of distinct informative terms, then FTS5 BM25 rank. Equal-BM25 selection at the result cut prefers the most recently remembered row; the returned rows are then presented in order of source observation time and validity start, then stable content/provenance fields, with row ID last. Candidates matching fewer than two distinct informative terms (or the sole term of a one-term query) are filtered. BM25 removes the systematic end-window omission, but tied records and the bounded candidate limit remain lexical heuristics. Recall cannot infer cross-language paraphrases or semantic equivalence, and a BM25 top-k result can omit a relevant candidate that ranks below the cutoff.

`TextIndex` is an internal interface around replace, stale-document removal, and search operations. SQLite FTS5 `unicode61 remove_diacritics 2` is the shipped code text tokenizer. Queries split into alphanumeric/underscore terms, including one- and two-character terms, and are matched with OR semantics. This returns whole-token matches; exact paths and extracted symbols have dedicated lookups. A fixed-fixture comparison found `unicode61` much smaller and faster than trigram with equal Recall@5/MRR for the tested content queries. The comparison method and SQLite versions are recorded in the performance guide. `rg` remains an external baseline.

## Configuration layers and project storage

Precedence, lowest to highest: built-in defaults, user-wide `config.json` (provider, model, consent) plus `credentials.json`, the trusted project's `.midnight/midnight.json` (can only disable semantic search or narrow the MCP policy), then flags. Database selection is `--db`, then the trusted project's `.midnight/midnight.sqlite3` found by walking up from the working directory, then the OS data directory. Trust is a per-machine allow-list (`trusted_projects.json`), because file ownership does not distinguish a database you created from one a clone delivered. The logic lives in `connect.rs` and `project.rs`; the CLI and MCP server share it. Code and memories remain in separate tables of whichever single database is selected.

## Current boundaries

There is no filesystem watcher. Every explicit full index command reconciles the file catalog, while metadata size/mtime avoids reading unchanged files unless `--verify-hashes` is set. The explicit `refresh-file` CLI command and `refresh_indexed_file` MCP tool provide a path-targeted update without walking the repository. They apply the same ignore, secret, file-size, symlink, and containment checks; the catalog is marked partial until a later full reconciliation catches missed changes, renames, deletes, and ignore-rule updates. No event queue or background process is required. On a generated 10k-file fixture, 30 MCP update-plus-search samples measured 379.0 ms full-reconciliation p95 versus 12.7 ms direct-refresh p95; every search saw fresh content, and a final full scan restored complete status. See the paired local evidence and fixture definition in the [performance report](performance.md). The older 10k/100 MiB full-reconciliation result (about 482 ms p95) is from a distinct workload.

Each Tree-sitter parse has a 250 ms budget checked through its progress callback; a timed-out parse keeps the lexical file entry, omits structural symbols, and marks the structural index incomplete. The callback is cooperative and may overshoot until Tree-sitter's next progress check; the 1 MiB file cap bounds each input. No allocator live-heap or mmap-page instrumentation is included. These are tracked limits, not claims of a strict operating-system wall-clock deadline.
