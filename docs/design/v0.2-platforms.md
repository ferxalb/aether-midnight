## Linux (x86_64, arm64)

**glibc vs musl — decision: ship glibc builds (`x86_64-unknown-linux-gnu`,
`aarch64-unknown-linux-gnu`) as the supported Linux artifacts; musl is not supported for local
embeddings.** Reasons: the `ort` crate here uses `load-dynamic` (the app `dlopen`s
`libonnxruntime.so` at runtime, path from `ORT_DYLIB_PATH` — verified from ort docs search results);
Microsoft's published Linux ONNX Runtime archives are glibc builds (asset names `onnxruntime-linux-x64-<v>.tgz`,
`onnxruntime-linux-aarch64-<v>.tgz` — verified for 1.23.x via mirror listing; glibc linkage itself
**not verified**), and a fully static musl binary cannot `dlopen` a glibc shared object. Build on an
old-glibc runner (e.g. ubuntu-22.04 container, glibc 2.35; pick the oldest that the Rust toolchain
supports) to maximize compatibility; record the minimum glibc in release notes after checking with
`objdump -T`.
A **musl lexical-only build** (`x86_64-unknown-linux-musl`, fully static, no ORT) is a possible
extra artifact: lexical search and cloud embeddings (TLS via `native-tls` needs OpenSSL — **conflict**:
musl static builds would need `rustls`; therefore musl is *deferred*, not promised).
Local embeddings per target: glibc Linux = supported through the pinned, SHA-256-verified ORT archive
installed by `runtime install`; musl = unavailable, `status` says so; Windows = pinned ORT zip.
ORT pins: current pin is 1.23.2 for macOS x86_64 only (`docs/platforms.md`). Newer releases exist
(search results mention 1.29/1.30 — **not verified**; do not bump without re-running the model
parity test). Part 2 adds a table of `(os, arch, version, url, sha256, size, inner path)` entries in
`runtime.rs` for `linux-x64`, `linux-aarch64`, `osx-arm64`, `win-x64`, `win-arm64`; each SHA-256
computed from the downloaded official archive on a trusted machine and committed, plus a test that
the pin table is complete and well-formed. No platform is marked supported until embedding parity (same
vectors within 1e-4 cosine of macOS on a fixed string set) is **measured** there.
Paths: XDG — config `$XDG_CONFIG_HOME` or `~/.config/aether-midnight`, data `$XDG_DATA_HOME` or
`~/.local/share/aether-midnight`, runtime (daemon socket) `$XDG_RUNTIME_DIR/midnight`; the existing
`AETHER_MIDNIGHT_CONFIG_DIR` override stays first. Check what `dirs` returns today before changing
(**not re-verified** in Part 1).

## Windows (x86_64, arm64)

Security guarantees vs macOS/Linux:

| Guarantee | Unix today | Windows design | Equivalent? |
| --- | --- | --- | --- |
| No symlink escape on repo reads | `openat(O_NOFOLLOW)` per component | Open with `CreateFileW(FILE_FLAG_OPEN_REPARSE_POINT)`; reject if attributes include `FILE_ATTRIBUTE_REPARSE_POINT` (symlinks, junctions, mount points); after open, `GetFinalPathNameByHandleW` and verify the final path starts with the canonical root; component-wise walk from the root handle using `NtCreateFile` relative opens is the strongest form | Weaker unless relative-open (`NtCreateFile` with `RootDirectory`) is used; final-path verification alone has a TOCTOU window between open and check (mitigated: check is on the open handle, not the path) |
| Walker does not follow links | `ignore` with `follow_links(false)` | Same; also skip reparse points explicitly | Equivalent |
| Private files 0600/0700 | `chmod` mode bits at creation | Create with an explicit DACL granting only the current user SID (and SYSTEM) and `PROTECTED_DACL`; verify by reading the DACL | Equivalent in intent; inheritance and admin override differ; Administrators can always read |
| Local IPC user-only | Unix socket 0600 in 0700 dir | Named pipe `\\.\pipe\midnight-<hash>` with user-only DACL and `PIPE_REJECT_REMOTE_CLIENTS`, `FILE_FLAG_FIRST_PIPE_INSTANCE` to prevent squatting | Equivalent in intent |
| Single-instance lock | `flock` (fs2) | `LockFileEx` via fs2 (same crate) | Equivalent |
| Case sensitivity / path form | case-sensitive paths | NTFS case-insensitive: normalize keys to a case-folded form for comparison only, store the real case; reject `\\?\`, device names (`CON`, `NUL`), alternate data streams (`:`) and trailing dots/spaces in repo-relative paths; use `/` as the stored separator (already done in `refresh_indexed_file`) | Needs new tests |
| Line endings | n/a | Index hash is over raw bytes (unchanged); line counting must treat `\r\n` as one line break; snippets strip `\r` | Needs tests |

Watcher: `notify` uses ReadDirectoryChangesW (**not verified**); buffer overflow → reconcile
(already designed). The PTY-based tests do not apply; mark them `#[cfg(unix)]`.
Build: `x86_64-pc-windows-msvc` and `aarch64-pc-windows-msvc`; C toolchain requirement of
`aws-lc-sys` (via `rainy-sdk`) and `native-tls` → SChannel on Windows (good: no OpenSSL).
Nothing here is validated without a Windows host: Part 2 must say "not run" until CI runs.

## CI

`.github/workflows/ci.yml`: on pull_request and push to main, matrix `{macos-latest,
ubuntu-latest, windows-latest}` (+ `ubuntu-24.04-arm`/`windows-11-arm` runners where available —
**verify current runner labels**), steps: checkout, `rustup` toolchain from `rust-version`, cache,
`cargo fmt --check` (one OS), `cargo clippy --all-targets --all-features -- -D warnings`,
`cargo test --locked`. Least-privilege `permissions: contents: read`. Actions pinned by commit SHA.
`release.yml`: tag trigger, build matrix for all targets, produce archives + `SHA256SUMS`, upload as
artifacts, then a separate publish job (see NPM) with `id-token: write` only there. Existing
`macos-release.yml` stays until the new one is validated.

## NPM

Layout: main package `@SCOPE/aether-midnight` (placeholder scope; real scope is an **open decision**)
with `bin` shim `bin/midnight.js` and `optionalDependencies` on per-platform packages
`@SCOPE/aether-midnight-darwin-arm64`, `-darwin-x64`, `-linux-x64-gnu`, `-linux-arm64-gnu`,
`-win32-x64`, `-win32-arm64`, each with `os`/`cpu` (and `libc` for linux) fields so npm installs only
the matching one, and containing only the binary + LICENSE. The shim resolves the platform package
with `require.resolve`, `spawn`s the binary with `stdio: "inherit"` and forwards exit code/signals;
no `postinstall` download, no network access at install (the binary comes from the registry tarball).
The shim verifies nothing at runtime beyond locating the file; integrity is npm's tarball integrity +
provenance; additionally the release publishes `SHA256SUMS` and the platform package `package.json`
carries the binary SHA-256 for `midnight --self-check` (compares the running binary hash — optional).
Publishing: GitHub Actions trusted publishing (OIDC): `permissions: id-token: write`, npm CLI ≥ 11.5.1
(one secondary source; **verify against docs.npmjs.com/trusted-publishers**), trusted publisher
configured per package on npmjs.com (each of the 7 packages needs its own entry — **not verified**),
`npm publish --provenance --access public`; provenance attestations are generated automatically with
trusted publishing from GitHub-hosted runners (verified from search results of the npm docs/GitHub
changelog). No long-lived `NPM_TOKEN`. Publish platform packages first, main package last, and only
after `SHA256SUMS` matches the artifacts built in the same run.
Signing: macOS — Developer ID Application + hardened runtime + notarization with `notarytool`;
**blocker recorded in `docs/release-signing.md`**: the Microsoft-signed ORT dylib may fail library
validation under a hardened runtime from another team; test actual loading before shipping signed
binaries, never re-sign ORT. Windows — Authenticode; options to research when choosing: Azure
Artifact Signing (formerly Trusted Signing), an EV/OV certificate in an HSM/cloud KMS, or SignPath
(OSS programme) — **recommendation not verified; re-research current Microsoft/SignPath terms**.
Workflows are written with `secrets.*` placeholders and `if: ${{ secrets.X != '' }}`-style guards
so unsigned CI still runs; no signing performed in Part 1/2 without credentials.
`scripts/install.sh` (curl installer with SHA-256 check) remains as an alternative, extended with Linux
targets once archives exist.

## Part 2 implementation decisions

Linux uses glibc artifacts and the existing XDG-aware directory resolver. Each added ORT pin
uses the archive digest from the Microsoft release API, confirmed against downloaded bytes,
and a separately hashed library member. Windows extracts only named members from the verified
ZIP using the inbox tar executable. It opens each source path component with reparse-point
handling, pins ancestors against rename/delete, checks the final paths of the open handles,
and reads from the verified leaf handle. This is still a Win32 path walk. Relative NT opens,
private ACLs, and named pipes remain open pending native validation. Windows status is
experimental and should not be used for confidential project databases until ACL validation.

Rejected: musl cannot use the pinned glibc ORT distribution; string-only Windows containment
is vulnerable to reparse and rename behavior; a downloading npm install script adds a second
integrity boundary. Expected failures are missing runtime dependencies (explicit loader error),
unavailable optional npm packages (shim reports the missing target), and wrong archives
(checksums gate extraction and packaging). Confidence is medium on the archive layout and
low on native Windows behavior. Require five successful native CI jobs, an installed CLI
smoke on each target, and runtime parity within 1e-4 cosine before changing platform tiers.

For rc.8 the package assembly records the verified binary digest in each native package and
runs offline npm pack checks in the workflow. Native Windows/Linux, npm package execution
and publishing, and signing are **NOT RUN**. The current Windows path walk, ACL gap, and
daemon transport gap remain as documented above. Platform tiers remain unchanged.
