# 0.1 Token savings (implemented in Part 1, Phase 1)

## Goal

The agent gets the most important evidence in the fewest tokens; ranking order and every
frozen-suite metric stay unchanged.

## Current state (verified in source)

`search_code_scoped` → `indexed_candidates` → `make_results` builds one result per candidate file with
a fixed-line excerpt (`excerpt`, default 3 lines from the matching line, 200-char line cap) and
`pack_context` charges `28 + tokens(path) + tokens(reason) + tokens(snippet)` per result, cutting the
tail or the last snippet at `token_budget` (64..8192, default 2048). Hybrid search (`embed.rs`
`search_code_on`) calls the same `code::pack_context`. Each result also carries
`index_generation`, `index_complete`, `score`, `score_breakdown`, `estimated_tokens` — redundant per
result because generation/completeness are per response.

## Decision record

**Chosen design** (all in `code.rs`, shared by lexical and hybrid):

1. *Symbol-bounded ranges.* For a matching line, look up the innermost indexed symbol containing it
   (`code_symbols.line_start/line_end`). Range = symbol signature line(s) (first line of the symbol, up
   to 2 lines) + a window of at most `context_lines` around the match, clipped to the symbol. If no
   symbol contains the match the existing fixed window is used. Multiple matching windows of one file
   that touch or overlap (gap ≤ 1 line) merge into one range; at most `MAX_RANGES_PER_FILE = 2` ranges
   per result. One result per file stays (current invariant), so ranking positions are unchanged.
2. *Progressive disclosure.* Default detail is `compact`: path, symbol, `ranges` (each with line span,
   short `ref` handle, and the bounded text). `open_range` accepts the handle
   (`{"ref": "..."}` or `path/line_start/line_end` as before) and expands to any ≤200-line range.
   Handle = `<hash12>@<start>-<end>` + path carried separately: concretely the string
   `"{path}#{start}-{end}@{content_hash[..12]}"`. It is stateless. `open_range` with a handle whose
   hash prefix differs from the current file hash returns `stale_handle: true`, `freshness: "stale"`,
   the *current* hash and **no content**; it never returns content labeled fresh for a stale handle.
3. *Session ledger* (interface `DeliveryLedger`, in-memory, per connection, owned by `mcp::Session`):
   key `(scope, path, start, end)` → `content_hash`. A range already delivered with the same hash is
   returned as `{"ref": ..., "delivered": true}` without text. Hash changed → text is sent again.
   Bounded to 512 entries (LRU), stores hashes and paths only — never query text. Opt-out per call:
   `"fresh_context": true` ignores and clears the ledger for that scope. The ledger is cleared on
   `initialize`. It lives behind the trait so the daemon (Phase 3) owns it per connection.
4. *Budget packing.* `pack` keeps candidate order. Per result it picks the largest detail level that
   fits: `full` (bounded ranges) → `signature` (symbol signature + the matching line) →
   `reference` (path, symbol, ref only). When the running total would exceed `token_budget`, levels are
   lowered starting from the result with the lowest `score / estimated_tokens` among results ranked
   *after* the exact-path/symbol class, then lower classes first; results at the tail are dropped
   only if even `reference` does not fit. Class boundaries are fixed before packing; a lower-class
   result can never displace or precede a higher-class result. Hard cap: `estimated_tokens ≤ token_budget`.
5. *Ranked, budgeted `repo_map`.* Additive `files` list on the MCP `repo_map` response (old fields kept),
   truncated to `token_budget` (default 1024). File score = `ln(1 + symbol_count) - 0.1 * depth`, plus a
   query bias (`query` argument): +2.0 if the path contains a term, +1.5 if a symbol name does. Ties
   break by path; deterministic (no clocks, no randomness). **Decision change during implementation:**
   the planned fan-in centrality (distinct referencing files via batched symbol-name lookups) was
   not implemented because it needs one FTS probe per symbol name; it is left designed for Part 2
   after its cost is measured. Ranking quality is **not measured**.
6. *Compact response shape.* Default response drops per-result `index_generation`,
   `index_complete`, `score_breakdown`, `estimated_tokens` and `snippet_truncated` (when false) and
   hoists `generation` and `complete` to the response next to `scope`. Kept per result: `path`,
   `freshness`, `match_reason`, `ranges`, `symbol`, `score` is dropped unless `explain: true`.
   `verbose: true` returns the exact pre-0.2 shape (including `snippet`, `line_start`, `line_end`).
   Every change is a contract change in `docs/api.md` with old and new examples.
7. *Estimator calibration.* The estimator stays `midnight-heuristic-v1`, labeled an estimate. The
   harness gets `calibrate-tokens --samples FILE --reference FILE`: it computes, offline, the ratio
   between the estimator and externally supplied reference counts for a sample of search responses.
   No network call or upload of code content is made by the harness; reference counts must be
   produced by the user with their tokenizer of choice (for example the provider's token-counting
   endpoint on the *public frozen fixture only*). Without a reference file the result is
   "not measured".

**Rejected alternatives**

- *Packer reorders by score per token (knapsack).* Violates "same paths, same order" and the
  evidence-class contract; a short low-class result could outrank an exact match. Rejected.
- *Server-side stateful handles (opaque ids in a table).* Break across daemon restart/fallback and
  need eviction rules; stateless content-hash handles give the same stale detection for free.
- *Always send diffs between searches.* History-dependent output cannot be verified by the harness
  and breaks if the client compacted its context; the ledger therefore only substitutes a reference
  for text the client was already sent, and `fresh_context` always overrides it.
- *Real tokenizer dependency.* Adds a model-specific vocabulary and a dependency for a heuristic that
  must only be monotone; calibration by ratio is enough.

**Three most likely failure modes**

1. *Client lost earlier text (compaction) and now receives only a reference.* The reference carries
   the handle, `open_range` expands in one call, `fresh_context` forces resend, and the ledger is
   cleared on `initialize`.
2. *Symbol index missing/stale (parse error, partial index) so ranges cannot be symbol-bounded.* Fall
   back to the fixed window; never fail the search; result is still labeled with the file freshness
   check that exists today (`current_text` hash compare).
3. *Compact shape breaks a consumer that read removed fields.* `verbose: true` restores the exact old
   shape; the change is listed in `docs/api.md`; AETHER Dots integration doc updated.

**Measurement and thresholds**

- Paths and order identical to the base commit on all queries of `benchmark/retrieval_queries.json`
  at the harness limit (5) and default limit (10): **pass = 0 differences**; frozen quality metrics
  (`retrieval-quality`, four memory fixtures) unchanged: **pass = identical JSON objects**.
- Estimated tokens and response bytes per query, before vs after, computed *externally* by the
  harness (`token-report`) from raw MCP `search_code` responses of either binary with one
  estimator, so the base binary needs no new code. Report p50/p95 and per-class deltas; **pass =
  after ≤ before on every query at the default settings, and p50 reduction reported honestly even if
  small**. Bytes and the estimate are reported separately; neither is a model-token count.
- Hard cap property test: `estimated_tokens ≤ token_budget` for budgets 64..8192.

**Confidence:** medium. Symbol-bounded ranges are low risk; the ledger and handle parts are new
surface. **What would change my mind:** if `token-report` shows no reduction at default settings
(the fixture has small files), keep the shape change but do not claim savings; if the symbol table
is empty for many files in real repositories, make the fixed window the default and symbol bounds
opt-in.
