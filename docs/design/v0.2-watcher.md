# 0.2 File watcher (implemented in Part 1, Phase 2)

## Goal

One-file edit visible in search ≤150 ms p95 (release binary), idle CPU ≈ 0, no polling, freshness
labels always truthful. Baseline: 474 ms p50 (`docs/performance-comparison.md`; a full scan
reconciles the repository on each update).

## Facts

- `notify` latest stable seen on docs.rs: **8.2.2** (verified, docs.rs/notify). Linux backend
  `INotifyWatcher`, macOS `macos_fsevent` (default feature) with optional `macos_kqueue`; the docs
  recommend `PollWatcher` manually for network filesystems, Docker-on-Apple-Silicon and `/proc`
  (verified). Windows uses `windows-sys` (ReadDirectoryChangesW — **not verified** in docs text).
  Whether `notify` silently substitutes polling on error: docs state no automatic fallback
  (verified absence); behavior of `recommended_watcher` on init failure is an error return
  (**not verified**, check when the crate is vendored).
- `notify-debouncer-mini`/`-full` spawn a tick thread (**not verified**); we avoid them.
- Not in `Cargo.lock` today (verified: no `notify`/`inotify`/`fsevent` entry; `mio` 1.2.4 and
  `windows-sys` exist). Adding it needs a one-time lockfile resolve.
- `refresh_indexed_file` (code.rs) takes the index lock, opens + migrates the DB, and hashes/parses
  one file: this, not the OS event, is the dominant per-update cost to measure.

## Decision record

**Chosen design**

- `notify = { version = "8.2", default-features = false, features = ["macos_fsevent"] }` as the OS
  event source only (FSEvents / inotify / ReadDirectoryChangesW). `PollWatcher` is never constructed;
  a backend init error becomes `watcher.state = "unavailable"` with the reason.
- Own debounce in `watch.rs`: a single thread blocks on `recv()` while idle (zero wakeups) and uses
  `recv_timeout(deadline)` only while paths are pending. Per-path coalescing in a
  `BTreeMap<PathBuf, Instant>`; flush when the newest event is ≥ `QUIET = 40 ms` old or the oldest
  is ≥ `MAX_WAIT = 200 ms` old. Batch of paths → `Sink::refresh(path)` each (single writer).
- Filtering before queueing: `.git/` contents are dropped except `HEAD`, `index`, `refs/heads/**`,
  and `packed-refs`; those set a `branch_change` flag. Other paths pass the same predicates as the
  indexer (`is_secret_path`, `is_vcs_metadata_path`, `default_generated_path`, `.gitignore`,
  `.aetherignore` via the `ignore` crate matcher built at start and rebuilt when an ignore file
  changes, size limit checked inside `refresh_indexed_file`). Ignore decisions are re-validated by
  `refresh_indexed_file` itself, so the watcher cannot index anything the indexer would not.
- Bounded queue: `MAX_PENDING_PATHS = 512` distinct paths and a bounded channel (4,096 events). On
  overflow, notify's rescan flag, or `branch_change`, the debouncer discards per-path work and issues
  **one** `Sink::reconcile()` (incremental `index_repository`, generation-based reconciliation, same
  semantics as today) after a `STORM_QUIET = 300 ms` quiet period.
- Directories created/renamed: watch registration is recursive in notify; new directories are
  registered by notify itself; to be safe a created directory triggers a bounded
  (`≤512` entries) per-file refresh of its children, over that → reconcile.
- `index_status` gains `watcher`: `{state: off|active|degraded|unavailable, reason, pending,
  last_event_ms, watches, overflow_count, reconcile_count}`.
- **inotify limits.** Registration cost is one watch per directory. We count directories with the
  ignore-aware walker *before* registering (skipping ignored dirs, `target`, `node_modules`, etc.,
  which is where the cost concentrates), compare against
  `/proc/sys/fs/inotify/max_user_watches` (read once), and refuse to start (state `degraded`,
  reason names the limit and the sysctl) rather than half-register. ENOSPC from the kernel at
  registration has the same outcome. A degraded repository is **never silently stale**: queries
  still compare the file hash at read time (existing behavior) and report `stale`, and
  `index_status.watcher.state` says why.
- **Freshness while an update is pending.** The label comes from the query-time content-hash check in
  `make_results`/`open_range`, which is independent of the watcher, so a result is `stale` between
  the edit and the refresh and `fresh` after. The watcher only shortens that window.
  `watcher.pending` makes the window visible.
- Hosting: `RepoWatcher::start(db, root, sink)`. In Phase 2 it is opt-in in a long-lived `mcp`
  process (`MIDNIGHT_WATCH=1`); in Phase 3 the daemon starts one per repository that a connection has
  indexed or queried, and stops it on idle. Two processes watching the same repo would both write;
  the index lock plus the daemon single writer make this safe, but default-on only in the daemon.

**Rejected alternatives**

- *`notify-debouncer-*` crates.* Tick thread (idle wakeups) violates "zero polling"; less control over
  storm handling.
- *Hand-written inotify via `libc` + FSEvents bindings.* Removes a dependency but we would own three
  platform backends and the Windows one; too much surface for Part 1.
- *`PollWatcher` fallback.* Violates zero polling; also hides degradation.
- *kqueue on macOS.* One fd per file; cannot scale.

**Three most likely failure modes**

1. *Event storm (checkout/rebase/`git stash`).* Bounded queue → single reconcile; test with 2,000
   synthetic events asserts exactly one reconcile and zero per-file refreshes.
2. *inotify watch exhaustion on a large tree.* Pre-count, refuse, report `degraded`; never partial.
3. *Editor save patterns (write-temp + rename, truncate + write) produce create/remove/modify
   bursts or transient missing files.* Per-path coalescing then a single `refresh_indexed_file`,
   which handles missing/unsafe files as a deletion; test with rename-over save.

**Measurement and thresholds** (release binary, final phase)

- One-file visibility: time from `fs::write` returning to the first `search_code` returning the new
  token as `fresh`, n ≥ 30, one request in flight. **Pass = p95 ≤ 150 ms.** If the p95 is above,
  report it as failed; do not tune the debounce below 20 ms just to pass.
- Idle CPU: `wait4`/`ps` CPU seconds over a 60 s idle window with watcher active. **Pass = ≤ 0.1 %
  of one core.**
- Storm: 1 reconcile, no `database is locked`.

**Confidence:** medium-high for correctness, medium for the 150 ms target (depends on per-refresh
cost, includes open+migrate until the daemon keeps a connection). **What would change my mind:**
measured `refresh_indexed_file` > 100 ms alone → keep a long-lived writer connection earlier
(Phase 3) before blaming the debounce; `notify` init semantics differing from the docs → write the
Linux backend over `libc` inotify.

## Dependency

The lockfile change is the only dependency change in Part 1. Resolve with the minimum command
(`cargo add notify@8.2 --no-default-features --features macos_fsevent` then `cargo check -j2`),
state it in the Phase 2 commit and HISTORY entry, and keep `--locked` for all later commands.

## Implementation notes (Phase 2) — decisions that changed or were refined

- **Verified in `notify` 8.2.2 sources:** `recommended_watcher` is `RecommendedWatcher::new` with no
  poll fallback; `Event::need_rescan()` exists; inotify reports `ErrorKind::MaxFilesWatch` on
  ENOSPC; FSEvents is created with latency 0.0; `mpsc::Sender` and closures are accepted as handlers.
- **`refresh_indexed_file` marks the catalog partial** (`is_complete=0`, `structural_complete=0`) on
  every call, which would leave a watched index permanently "incomplete". Added
  `code::refresh_watched_file` (same body, completeness flags preserved; a changed file with a parse
  error still clears `structural_complete`). Valid only because the watcher reconciles at start, on
  overflow/rescan, on branch change, on ignore-rule edits, on removed directories and on backend errors.
  The public tool is unchanged.
- **Linux registers one non-recursive watch per directory** found by an ignore-aware walk (never
  `.git`, never ignored trees) instead of notify's recursive mode, so `target/` or `node_modules/`
  cannot exhaust `max_user_watches`; the count is checked against the sysctl before registering.
  macOS/Windows use one recursive watch plus a path filter.
- **Opt-in until the daemon exists:** `MIDNIGHT_WATCH=1`; the daemon sets the default on.
  `MIDNIGHT_WATCH=0` always wins.
- Debounce constants: quiet 40 ms, max wait 200 ms, storm quiet 300 ms (max 2 s), 512 pending
  paths, event queue 4,096. Removed/renamed directories and created directories with more than 512
  files trigger the reconcile path. A failed refresh is retried once.
- Known gaps: nested `.gitignore` rules are enforced by `refresh_watched_file` (via
  `target_is_eligible`), not by the watcher's pre-filter (root-level ignore files and
  `.git/info/exclude` only), so ignored files in nested ignore scopes cost one rejected refresh per
  event burst; Windows is untested; hard-linked or bind-mounted trees are not handled.
