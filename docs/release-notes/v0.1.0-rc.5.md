Fifth prerelease of AETHER Midnight: a local-first engine for deterministic code search and explicit agent memory.

**Install** (macOS, Universal 2, user-local, no sudo):

```sh
curl --proto '=https' --tlsv1.2 -fsSL https://github.com/ferxalbs/aether-midnight/releases/download/v0.1.0-rc.5/install.sh | sh -s -- --no-runtime
```

Already on rc.4? Run `midnight update`.

**Database:** no schema change (still schema 7). An rc.4 database opens unchanged, and this build's database still opens with rc.4.

**Read before upgrading: this release changes output fields.** Clients that parse `search_code` / `search` results or `complete` must be updated:

- `scope` moved from every code-search result to the response (`response.scope`). `freshness`, `index_generation` and `index_complete` stay on each result.
- `complete` (indexing reports and `index_status`) and `index_complete` (`search_code`, `open_range`) now mean the file catalog and lexical index are complete. They no longer turn `false` because a file failed to parse. `structural_complete` stays separate, and `index_status` adds `parse_error_files` and `parse_error_paths` (at most 20). `list_symbols` and `repo_map` still report incomplete while any file has a parse error, because their data is structural.
- Search snippets default to 3 lines (was 8) starting at the matching line. Each snippet line is capped at 200 characters, cut around the match, and marked with `…`; `snippet_truncated` and the response `truncated` are set when that happens. New `context_lines` argument (MCP) and `--context-lines` (CLI), 1 to 8, to ask for more. `open_range` still returns full lines.
- For semantic hits, `line_end` is now the last line shown.

**Changes since v0.1.0-rc.4**

- **Fix:** one file Tree-sitter cannot parse no longer leaves the whole repository `complete: false`. The case found in practice was a valid TSX file with a bare `&` in JSX text; the parse took about 1 ms, so it was a grammar limitation and not the 250 ms budget. Such files stay searchable by text.
- **Fix:** a file with the rarest query term could rank below files that matched only common words, because results with the same saturated lexical score were ordered by path. They are now ordered by BM25 first. On a synthetic 121-file repository with real OpenRouter embeddings, the target file went from rank 6 to 7 to rank 1 in `hybrid` (5 runs each) and from 10th to 1st in `lexical`. The frozen retrieval fixture (4 files, MRR 1.0) is unchanged in every metric and in the rank of every relevant file; it is too small to show the improvement.
- **Smaller results for agents:** on four queries with limit 3 over this repository, estimated tokens per response went from 3470 to 1220 and the JSON from 14353 to 7199 bytes, with the same result paths in the same order. The estimator is the project heuristic, not a model tokenizer.

**Known limitations**

- The binary is **not Developer ID signed or notarized**; Gatekeeper rejects it.
- Tested through scripted MCP sessions and the automated test suite. Claude Code and Codex were run against rc.4, not against this build; Claude Desktop has never been run.
- Rainy embeddings have **not** been verified against a real account. OpenRouter was exercised on synthetic fixtures for this release.
- Tested on an Intel Mac; the arm64 slice is built and packaged but was not run by the maintainer.
- Exact-phrase queries are an OR of terms ranked by BM25 with no phrase awareness: a file containing the phrase can fall outside the top 10 when other files contain the words separately and more often (measured with a 300-line file). The ranking fix above does not address this.
- `hybrid` and `semantic` results can vary between runs with a remote provider, because the provider's query embedding is not deterministic.
- Two processes writing to the same database at once can fail with `database is locked`.
