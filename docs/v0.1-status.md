## Correctness changes

The pinned `rainy-sdk` 0.6.51 decoder requires optional fields and loses some 4xx
statuses. The narrow cloud compatibility adapter retains SDK request/configuration and
endpoint validation, using the already-present `ureq` transport for status-preserving,
bounded wire decoding. No dependencies, database schema, local inference, retrieval
ranking, MCP or HTTP surface were added or changed.

Contracts reviewed: [OpenRouter embeddings](https://openrouter.ai/docs/api/api-reference/embeddings/create-embeddings),
[official Rainy SDK](https://github.com/enosislabs/rainy-sdk), and the locked SDK source.
Optional metadata is ignored; mandatory vector content remains strictly typed. With no
indices, list order is the mapping to inputs; providers that cannot guarantee that order
must return indices. Mixed responses fail closed. Live provider behavior is unverified.

A failed embed exits nonzero and says committed vectors are retained and re-running
`embed` resumes. Search exposes `semantic_coverage` and a partial-coverage notice after
a provider recovers. No changes to persistence/ranking were necessary: the existing
coverage implementation already reports this correctly. The regression now actually
checks that recovery path instead of checking only lexical fallback during an outage.

## Quality and performance

Frozen memory v2: MRR **0.891667**, recall@1 **0.55**, recall@10 **0.975**.
Single-term v1 MRR **0.896825**; adversarial MRR/recall@1 **1.0**. No labels or retrieval
implementation were edited. These remain quality baselines, not semantic relevance claims.
The native macOS retrieval gate described in `retrieval-v04.md` is still pending; the
small lexical smoke does not close that historical large-scale gate.

Final measurements (5 queries each): 10k exact KNN 109.6 ms wall / 100.8 ms CPU /
15.55 MiB RSS; 100k 483.1 ms / 472.6 ms / 18.95 MiB. These include process start and
loopback query embedding. Fresh local semantic query: 4.491 s wall / 4.742 s CPU /
1.46 GiB RSS median. Warm 512-text embed: 6.683 s wall / 27.168 s CPU, including load;
16-versus-512 incremental estimate: 4.31 ms/text (one pair, short synthetic texts).
Method, ranges and limitations: [performance.md](performance.md).
A fresh local semantic CLI process still has approximately a four-second model-load
cost and approximately 1.5 GiB inference peak RSS. There is no semantic MCP/HTTP mode
in this release. Warm-batch throughput is measured through `embed`, with incremental
warm cost estimated from 16 versus 512 texts; it is not persistent query-server latency.
